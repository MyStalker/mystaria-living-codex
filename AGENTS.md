# Living Codex development

This repository implements the public website. Canon and the teaching prose live upstream.

1. Retrieve latest main of `MyStalker/mystaria-codex`; start with the Canon Index, Canon Changelog, owning subject references, repository instructions, and visual guide. The author's November 25 instruction makes **HP/d20 with Training Points the current player-facing game, without a playtest label**. It does not select missing prices, racial Skill arrays, or unfinished conversions.
2. Public teaching pages are in the canon repository's `public/players/`. When an approved change affects players, update its owning detailed subject/changelog and the affected teaching guide together. Do not duplicate guide prose in this website repository. Teach the resulting rule directly; history, discarded mechanics, and simulation evidence remain upstream.
3. Read `content/reading-manifest.json`, `content/public-manifest.json`, README, and maintenance notes before changing ingestion. Routes come from stable guide entries; source moves retain identifiers. New public documents need explicit selection and privacy review.
4. Render Markdown and `::: detail` optional sections. `{{table:...}}` expansions use explicitly selected public source blocks; ambiguous/missing selectors must fail. No arbitrary path interpolation or automatic publication of entire repositories. Proposals never become player options merely by being on main.
5. Preserve the inherited illustration, theme, `mystaria-theme` and `mystaria-bookmarks` storage keys, illustrative stories, and old routes. Do not generate new canon art. Keep ordinary reading free of approval logs, build hashes, repeated status badges, or obsolete mechanics.
6. Build using `python scripts/build.py` with pinned dependencies. Production always retrieves current sources. `--offline` is only for verified local development caches. Stage and validate before replacing output; failures retain the accepted output and production deploy.
7. Run Python tests, whole-artifact validation, JS syntax checks, and calculator assertions. The synthetic publishing test must use an isolated cache and explicit fixture inclusion, never unapproved upstream canon. Check representative desktop/mobile lessons, search, optional sections, fragments, themes, bookmarks, and tables on a Netlify permalink.
8. Use the existing Netlify project and URL. Develop substantial website changes on a branch and use local checks or free Deploy Previews. Production releases go through the single **Queue reviewed Codex release** workflow; do not POST build hooks, manually retry production deploys, or upload successive work-in-progress builds. `content/publishing-policy.json` holds the shared release limits. Inspect the workflow summary and production `/build.json`; a commit, green CI or queued build is not a verified live release. Never delete/recreate the site or its history.
9. Routine approved docs and reversible website work follow the authorized main-branch workflow. Respect protections and review destructive/high-risk operations. Keep cache, secrets, raw recovery archives, campaign records, GM-only material, and local build dependencies out of Git and `dist`.
10. Report changed files/repositories, exact source commits, tests, live deployment status, limits, and any actual author action. Future content updates need editorial canon maintenance, not a local manual website rebuild.
11. Save all related approved subject, changelog, index and player-guide edits in **one atomic commit** where possible (Git data tree/commit APIs support this). Never enable per-file production hooks. The central queue compares generated public artifacts, batches releases at least six hours apart, and permits at most 2 requests per rolling 24 hours and 12 per rolling 30 days by default. Manual requests/retries count too; no silent budget overrides. Unconfirmed releases pause further requests until inspected. See `docs/PUBLISHING-SAFEGUARDS.md` for recovery and verification limits.
